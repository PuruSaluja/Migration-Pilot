- 2026-11-21 (P2-04), design points for the owner (no SPEC [REC] change, so no §20 row):
  - **Fail closed on what a tree cannot hold.** An export refuses (and so a pause fails, falling back to crash-style recovery from the last host snapshot, §10.1) if the workspace holds a FIFO, socket, device, setuid/setgid file or an unrepresentable name. Flip to "skip and record" if a stray `.sock` file aborting a pause worries you. Under gVisor a FIFO or socket created in the sandbox never reaches the host at all (`--host-fifo none`); under runc it does and is refused.
  - **What an export keeps:** everything under the workspace including `.git`, `node_modules` and other dependency directories (so a resume needs no reinstall), empty directories, the exec bit (other mode bits are reduced to 644/755 as in git), and file modification times (so incremental builds and caches still line up). Not kept: ownership (files belong to the host user), directory modes (0755), hard links, extended attributes. The manifest (`ExportManifest`) covers files and links only, as before; empty directories are kept physically in the export directory but are not part of the digest.
  - **The export directory is not trusted on restore.** It is read with the same containment as a workspace, so a link planted in it is copied as a link and never read through, and anything added, removed or changed makes the digest differ and the restore is refused with the workspace emptied. The manifest itself is never trusted either: it must hash to the checkpoint's digest, which the orchestrator reads from the DB (`RunState.export_digest`).
  - **`restore` never merges.** The workspace path must be absent or an empty real directory. For resume the orchestrator must `reap` the crashed or paused run's containers first (§10.1), then restore into a fresh path or an emptied one.
  - **A sandbox that cannot be resumed (BROKEN) refuses `export_workspace`; `destroy()` it first.** After `destroy` verified the container gone, the workspace is exported without a freeze, since nothing mounts it. A cancelled export keeps the sandbox frozen until the copy thread has finished, so the container never resumes under a running copy; the orchestrator's other `Workspace` work under `frozen()` (P3-06 diffs and snapshots) needs the same care: a thread that outlives its cancelled caller must be waited for before leaving `frozen()`.
  - Export and restore copy file contents once (no reflinks or hard links), so a paused run with a large `node_modules` costs one full copy each way; `runs/` is on the 50 GB loopback.
  - Not changed: the frozen interfaces. `HostWorkspace.export_to`/`restore_from`/`clear` are extra methods on the implementation, not on the `Workspace` protocol.
  - For P4-18 (pause/resume): store `ExportManifest` JSON next to the export (the checkpoint holds only `export_dir` and `export_digest`); a resume loads that manifest, passes `expected_digest=RunState.export_digest`, and must treat `ExportIntegrityError` as "export unusable: fall back to the latest host snapshot".

- 2026-11-21 (P2-05), design points for the owner (no SPEC [REC] change, so no §20 row):
  - **Overshoot is bounded by the poll interval, not zero.** The poll is every second (`DISK_POLL_S`), so a fast writer passes the limit before it is stopped: measured ~200 MiB past a 20 MiB limit at a 0.3 s poll (about 300 MB/s). At the real 20 GB limit that is a few hundred MB; the fixed-size `runs/` filesystem is the hard ceiling behind it.
  - **A command that finishes before the first poll is never killed**, so the command that frees space on an over-limit workspace (`rm`) can run; any longer command on an over-limit workspace is killed at its first poll.
  - **A workspace that cannot be measured stops the command** (three failed polls in a row, or a tree deeper than 256 levels): running unguarded is the worse failure. The note on stderr says why.
  - **Measured:** allocated blocks of every file, link and directory including `.git` and dependency directories, hard links once, sparse files by what they allocate (like `du`). Metadata only: no regular file is opened and no link followed (tested with a swapped-in link and a FIFO), so no freeze is needed. Only the workspace is measured today; the package cache joins in P2-07 (add its directory as a second meter in `DockerSandbox`).
  - **`/tmp` cap = min(1 GiB, memory limit / 2)**, my pick (the spec gives no number): tmpfs pages are memory, and with the 1 GiB test limit a 1 GiB cap would hit the memory limit first, which under gVisor kills the whole sandbox. Flip the 1 GiB if real builds need more scratch space.
  - **`check_runs_filesystem(path, disk_gb=...)` is a function, not yet wired in.** Problems (root filesystem, in memory, smaller than one run's `disk_gb`, missing) are for the sandbox selftest (P2-19) and orchestrator startup (P3-05) to fail on; a real partition instead of a loop device is only a warning. It is deliberately not called from `create`: the tests' temp directories are on the root filesystem.
  - For the diagnoser/verifier: `ExecResult.killed_disk_limit` is the ENV_INSTALL signal (§9.3); nothing maps it yet.
